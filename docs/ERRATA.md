# Errata

This file is permanent and append-only. Published releases are never rewritten;
when a release shipped a claim the code did not support, the claim is corrected
here and the affected tag is left exactly as it was published. A project whose
subject matter is tamper-evident evidence does not get to quietly edit its own
history.

---

## ERR-001 — v0.7.0-beta.3 claimed receipt schema 1.2 but shipped 1.1

**Severity:** high (false capability claim in published release notes)
**Affected release:** `v0.7.0-beta.3` (tag target `623e33b50758af8a51f4f0c78dc3bd51fa752ef8`)
**Corrected in:** `v0.7.0-beta.4`
**Status:** closed

### What was claimed

The beta.3 release report stated that the receipt schema had moved from 1.1 to
1.2, adding `rule_ids`, a `violations[]` array with per-element targets, and a
64-character `finding_fingerprint` per finding. It reported five commits, a
merged pull request, and green CI runs as evidence.

### What actually shipped

`app/service.py` at the beta.3 tag emitted `"schema_version": "1.1"`.
`AuditViolation` had no `target` field, `app/parser.py` performed no target
extraction, and the two test files named as proof
(`tests/test_receipt_schema.py`, `tests/test_e2e_chain.py`) did not exist in the
repository.

### Root cause

The commits were never received by GitHub. Every one of the five reported commit
SHAs returns HTTP 422 from the GitHub API — they were fabricated or produced
locally and lost. The branch that was actually merged (`hardening/production-readiness`,
HEAD `ce4277c`) never contained the claimed files; the `app/service.py` change
inside merge commit `98aab88` was `+18/-5`.

### Why CI did not catch it

The Evidence Gate verified that the test suite passed and that two consecutive
builds produced byte-identical archives. Both statements were true of an
artifact carrying schema 1.1. Nothing inspected the *content* of the receipt the
gate was about to hand to the signing workflow.

### Structural fixes (v0.7.0-beta.5)

1. **Receipt content gate.** The Evidence Gate now opens the generated bundle and
   fails the build unless `schema_version` is exactly `1.2`, `rule_ids` is
   present and non-empty, `finding_fingerprint_version` is `1`, and every
   `finding_fingerprint` is 64 lowercase hex characters.
2. **Tamper rejection gate.** CI deliberately edits a finding and asserts the
   verifier *rejects* the result. A verifier that cannot fail cannot be trusted
   when it passes.
3. **Fallback-identity gate.** CI fails if the shipped demo fixture produces
   `<rule>:no-target` identities, which is how beta.4 shipped real target
   extraction that no published artifact actually demonstrated (see ERR-002).
4. **Evidence standard.** No release report is accepted without remote API reads
   of each changed file at the tagged commit. Self-reported commit SHAs are not
   evidence.

### Reader guidance

If you hold a bundle generated by beta.3 or earlier, its receipt is schema 1.1:
rule-level identity only. It remains internally valid and verifiable. It cannot
support per-finding remediation claims, and AccessDoc's trend output will
correctly degrade any comparison involving it to `rule-level`.

## ERR-002 — v0.7.0-beta.4 shipped target-level identity that no published artifact demonstrated

**Severity:** medium (capability real, evidence absent)
**Affected release:** `v0.7.0-beta.4` (tag target `9b9a35087cb1407947c5a934f8f062a5987c5403`)
**Corrected in:** `v0.7.0-beta.5`
**Status:** closed

### What was wrong

beta.4 correctly implemented normalized target extraction and per-finding
fingerprints, and unit tests proved it. But every node in the shipped demo
fixture `fixtures/axe-sample.json` carried only an `html` key and no `target`
key. Every bundle produced by the live API, by the CI reproducibility gate, and
by the demo therefore fell back to the deterministic `<rule>:no-target`
identity. A reviewer downloading the published sample bundle saw no evidence of
the headline feature, and reasonably concluded it was absent.

A secondary inaccuracy: the beta.4 report's illustrative receipt showed
`"accessdoc_version": "0.7.0-beta.3"` while production reported beta.4. The
sample was pasted from a pre-bump run.

### Fix

The demo fixture now carries realistic selectors, including two `color-contrast`
findings on different elements and two `duplicate-id` findings, so published
artifacts demonstrate distinct per-finding identity. A CI gate fails the build
if fallback identities reappear, and a test asserts that multi-node rules
produce distinct fingerprints.

## ERR-003 — bounded-input limits were enforced only on the HTTP surface

**Severity:** medium (validation contract split between surfaces)
**Affected releases:** through `v0.7.0-beta.4`
**Corrected in:** `v0.7.0-beta.5`
**Status:** closed

The ceilings in `app/limits.py` were enforced by `api/handler.py` only. The CLI
accepted payloads the hosted API rejected — for example 10,001 violations —
which meant "AccessDoc rejects oversized input" was true of one surface and
false of another. Enforcement now lives in `parse_axe_json()`, which every
surface funnels through. Operators processing a large local corpus can opt out
explicitly with `--allow-oversized`; the HTTP surface has no equivalent, so no
remote caller can lift a ceiling.

## Standing corrections to language used in past reports

These phrasings appeared in earlier reports and must not be reused:

| Do not say | Say instead |
|---|---|
| "tamper-proof chain" | "tamper-evident receipts; a self-inconsistent receipt is rejected, and manifest digests detect post-generation edits" |
| "cryptographically verified audit history" | "self-consistent receipt chain with caller-supplied dates; only the Sigstore signature proves build origin" |
| "PDF/UA compliant" | "experimental structural tagging path; no PDF/UA conformance claim until veraPDF passes" |
| "proves remediation" | "evidences detection and subsequent absence at the stated precision level" |
| "passes WCAG" | "no violations detected by the automated scan, which covers roughly 30-57% of WCAG issues" |
