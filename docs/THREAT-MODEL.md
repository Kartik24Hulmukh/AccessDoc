# AccessDoc Threat Model

> **This document is plain-language security documentation. It is not legal advice.**

## What AccessDoc protects against

### Tamper detection (accidental corruption + naive tampering)

The evidence bundle uses two layers of integrity protection:

1. **SHA-256 manifest** (`manifest.json`): Every file in the bundle has its
   SHA-256 hash recorded in the manifest. `validate_bundle()` recomputes every
   hash and compares it to the manifest. If any file has been modified, added,
   or removed, validation fails with a clear error message.

2. **in-toto attestation** (`attestation.intoto.json`): An unsigned in-toto
   v1 DSSE envelope whose `subject` and `materials` arrays contain SHA-256
   digests of every file in the bundle. This provides a second independent
   record of the expected file hashes.

**What this detects:**
- Accidental file corruption (bit rot, transfer errors)
- Naive tampering (someone edits report.pdf in a ZIP tool)
- File addition or removal (injecting or deleting evidence)

**What this does NOT detect:**
- A motivated attacker who can regenerate the entire bundle (including the
  manifest and attestation) from modified input. Because the attestation is
  **unsigned**, there is no cryptographic proof of *origin*. An attacker with
  AccessDoc installed can produce a valid-looking bundle from any input.

### Reproducible bundles (byte-identical output)

With `reportlab.rl_config.invariant = 1` (set in `app/reporter.py`), the PDF
is fully deterministic: `/CreationDate`, `/ModDate`, and the `/ID` digest are
replaced with fixed values. Combined with a fixed `audit_date` input, the
**entire bundle is byte-reproducible end-to-end** — same input produces the
same SHA-256 for every file including the PDF, manifest, and in-toto
attestation.

This has been tested and verified:
- Same input, same environment: byte-identical bundle ✅
- Same input, different timezones (TZ=UTC vs TZ=Asia/Calcutta): byte-identical ✅
- 10,000-violation benchmark: 13.36s, 355 KB bundle, peak RSS 330 MB ✅

**What this proves:** That two bundles with the same SHA-256 were generated
from the same input. This supports the product's core claim of reproducible
evidence.

**What this does NOT prove:** That a specific person or organisation generated
the bundle. Without signing, anyone with AccessDoc and the same input can
produce the same bundle.

### Trend chain (prev_receipt_sha256)

The `trend.json` file contains a `prev_receipt_sha256` field — a SHA-256
digest of the prior receipt. This creates a hash chain between scans.

**What it is:** A SHA-256 of the prior receipt dict (sorted keys, compact JSON),
computed by `_sha256_of_receipt()` in `app/timeseries.py`. It links the current
scan to a specific prior receipt.

**What it proves:** That the current scan references a specific prior receipt.
If the prior receipt is altered, the `prev_receipt_sha256` will not match.

**What it does NOT prove:**
- That the prior receipt was generated by a specific person or organisation
  (the attestation is unsigned)
- That the chain is tamper-proof against someone who can regenerate both the
  prior receipt and the current bundle

**Relationship to manifest:** The `receipt.json` file is itself a bundle
artifact whose SHA-256 is recorded in `manifest.json` and the in-toto
attestation. So the receipt is protected by the same tamper-detection layer
as every other file. The `prev_receipt_sha256` in `trend.json` is an
additional cross-scan chain link, not a replacement for the manifest hash.

## What AccessDoc does NOT protect against

### Unsigned attestation

The in-toto attestation is currently **unsigned**. This means:

- ✅ Detects accidental corruption and naive tampering
- ✅ Provides a verifiable record of what files were in the bundle at generation time
- ❌ Does NOT prove who generated the bundle
- ❌ Does NOT prevent a motivated attacker from generating a fraudulent bundle
- ❌ Does NOT provide non-repudiation

A signing mechanism (sigstore/cosign) is planned for a future release. See
`docs/signing-plan.md` for the proposed approach.

### PDF is not accessible (untagged)

The generated `report.pdf` is an **untagged PDF** — it has no structure tree,
no PDF/UA compliance, and no table structure elements. Screen readers cannot
navigate it semantically. The PDF does have a meaningful document title,
language (`/Lang=en`), author, and subject (set in Phase 3.2).

**The HTML companion (`report.html`) is the accessible artifact.** It has
zero axe-core violations at critical/serious/moderate impact levels, tested
at both default and 320px viewport width (WCAG 1.4.10 reflow).

An experimental WeasyPrint path (`--pdf-engine=weasyprint`) can produce a
tagged PDF/UA-1 with `/StructTreeRoot`, `/MarkInfo`, and table structure
elements. WeasyPrint output IS byte-reproducible (verified across 3 runs).
The only non-determinism in the bundle comes from the in-toto `_utc_now()`
timestamp, which affects both engines equally. See `docs/pdf-ua-plan.md`
for the full decision document with measured results.

### Automated coverage ceiling

Automated accessibility testing tools (axe-core) detect approximately
**30–57%** of WCAG issues (Deque Systems 2022; GDS 2017). This means:

- A clean automated scan does **not** mean a site is accessible
- The bundle documents what the scanner found, not what it didn't check
- Manual and assistive-technology testing is required for a conformance claim
- Every bundle and report states this limitation explicitly

### VPAT output is a DRAFT

The `vpat-draft.html` output is marked **"DRAFT — AUTOMATED EVIDENCE ONLY — NOT
A CERTIFIED VPAT"**. It is:

- A starting structure for a human-reviewed VPAT
- Not a certification
- Not a conformance claim
- Not legal advice

A real VPAT requires manual testing by a qualified evaluator.

### No network security

AccessDoc's deterministic core makes no network calls. The optional `scan`
companion (Playwright + axe-core) fetches axe-core from a CDN if not provided
locally. This fetch is not authenticated or integrity-checked by default.
For production use, set `ACCESSDOC_AXE_PATH` to a locally-verified axe-core
file.

### No secret management

AccessDoc does not handle, store, or transmit secrets. The bundle contains
only scan results and metadata. If the scan input contains sensitive
information (e.g., authenticated page content), that information will be
included in the bundle.

## Trust model summary

| Threat | Protected? | How |
|--------|-----------|-----|
| Accidental file corruption | ✅ | SHA-256 manifest + in-toto digests |
| Naive tampering (edit a file in the ZIP) | ✅ | Hash mismatch detected by validate_bundle |
| File injection/removal | ✅ | Manifest membership check |
| Bundle reproducibility | ✅ | reportlab.rl_config.invariant=1 + fixed audit_date |
| Timezone-dependent output | ✅ | Tested: TZ=UTC vs TZ=Asia/Calcutta → identical |
| Attacker regenerates entire bundle | ❌ | Attestation is unsigned — no origin proof |
| Attacker forges the timestamp | ❌ | Timestamp is in the unsigned attestation |
| PDF accessibility for screen readers | ❌ | PDF is untagged — HTML is the accessible artifact. See docs/pdf-ua-plan.md |
| Automated scan misses WCAG issues | ⚠️ (documented) | 30-57% coverage ceiling stated in every output |
| VPAT used as certification | ⚠️ (documented) | Marked DRAFT in red; not a certified VPAT |

## Future improvements

1. **Signing** (see `docs/signing-plan.md`): sigstore/cosign integration to
   sign the in-toto attestation, providing origin proof and non-repudiation.
2. **PDF/UA tagging** (see `docs/pdf-ua-plan.md`): three options evaluated
   with measured results — ReportLab Plus (commercial, preserves determinism),
   WeasyPrint (open-source, tagged but NOT deterministic), or ship HTML as
   the accessible artifact (current, pragmatic). Owner decision required.
3. **axe-core integrity verification**: hash-pin the axe-core version and
   verify it at load time.
